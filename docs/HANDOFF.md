# SaveSync — Handoff: запуск разработки

> Этот документ — единая точка входа для новой рабочей сессии. Содержит требования, архитектуру, процесс (Git Flow + GitHub), тестирование и установку.
> Детали: `plan.md` (полный план), `research/RESEARCH.md` (ресерч рисков), `design/` (UX-мокапы: `desktop-app.html`, `decky-panel.html`, `design-system.md`).

---

## 0. Суть проекта

Кроссплатформенный клиент синхронизации сохранений игр между Windows PC и Steam Deck (SteamOS). Аналог Steam Cloud, но: любые игры (не только Steam), версионирование, конфликты, бэкапы, каналы синхронизации — Яндекс.Диск / Google Drive и/или прямая LAN-синхронизация. Стек: **Rust**.

**MVP (итерация 1): только ручная синхронизация** — пользователь жмёт «Синхронизировать». Никаких таймеров, опросов облака, watcher-триггеров, автодетекта запуска/выхода игры. Автотриггеры — итерация 2, требуют отдельного ресерча.

---

## 1. Архитектура (кратко)

Единый Rust-демон `savesync-daemon` со всей логикой + тонкие UI по IPC:

- **Демон**: sync engine (снапшоты zip/zstd, blake3, иммутабельные версии, локи, конфликты), сканер игр (парсер локального Steam appinfo + свой репо манифестов `savesync-manifests` + ручные правила), бэкенды (YandexDisk / GoogleDrive / LAN), бэкапы, IPC-сервер (unix socket на Linux, named pipe на Windows, JSON-RPC).
- **Десктопное приложение** (Windows + SteamOS Desktop Mode): egui/eframe или Tauri — решить на старте M4, дизайн нейтрален. Тёмная Steam-палитра: `#171a21 / #1b2838 / #66c0f4`.
- **Decky-плагин («шторка», 360 px)**: React UI → Python-прокси → демон по unix socket. Только статус, кнопка «Синхронизировать», баннер конфликта, pairing. Конфликт-резолвера в шторке НЕТ.
- Windows: user-context агент (НЕ SYSTEM-сервис), автозапуск, трей. Код-сайнинг обязателен (антивирусы).
- SteamOS: systemd user unit, автономен без Decky.

**Идентификация игр:** `game_key` = нормализованный slug имени игры (store-агностично), не Steam appid. Источники путей (по приоритету): локальный Steam appinfo (`appinfo.vdf`, UFS-конфиги — полностью наш источник) → свой репо `savesync-manifests` (CC BY-NC-SA; наполняется генератором из appinfo + импортером PCGamingWiki + комьюнити-PR) → ручные правила (`custom:<slug>`). Матчинг устройств через `index.json`. Чужих API в рантайме нет.

**Каналы независимы:** облако и LAN — два самостоятельных бэкенда одного движка; настраиваются отдельно, можно любой/оба/ни одного (тогда только локальные бэкапы). В UI — две независимые карточки, не шаги визарда.

**Стратегия синхронизации (§2.1 plan.md):** снапшоты, не «живые» папки; новая версия = timestamp + изменённый blake3; конфликт = ветвление с политиками per-game (авто-новейший / спросить / keep-both, всегда обратимо); перед затиранием локальных сейвов — авто-бэкап движка.

**Бэкапы (§2.2 plan.md):** переносимый файл `*.ssbak` (zip/zstd + manifest.json), ручной экспорт/импорт, авто-бэкапы по расписанию с retention, передача любым способом (USB и т.п.).

**Ключевые риски (research/RESEARCH.md):** непереносимые сейвы (FromSoftware — ключ от SteamID64, GameMaker secure_save) → свой блок/варн-лист; inotify не ловит mmap под Proton; сейвы в реестре Proton-префикса; rclone — анти-паттерн; Google Testing-статус убивает refresh-токены за 7 дней; keyutils на Linux не персистентен → Secret Service + fallback.

## 2. Git Flow + GitHub (обязательный процесс)

**Репозиторий:** приватный, GitHub. Если remote ещё не создан — создать через `gh repo create savesync --private` либо привязать существующий (`git remote add origin <url>`). Все пуши — только туда.

**Ветки (Git Flow):**
- `main` — стабильные релизы, теги `vX.Y.Z`. Прямые коммиты запрещены.
- `develop` — интеграционная ветка, всегда собирается, тесты зелёные.
- `feature/<name>` — от `develop`, merge обратно через PR (`--no-ff`).
- `release/<X.Y.Z>` — подготовка релиза: только багфиксы и версии; merge в `main` и `develop`.
- `hotfix/<name>` — от `main`, merge в `main` и `develop`.

**Правила:**
- Conventional Commits: `feat:`, `fix:`, `chore:`, `test:`, `docs:`, `ci:`, `refactor:`.
- PR в `develop` обязателен даже для соло-работы (история + CI). Merge — squash или `--no-ff` для feature.
- CI (GitHub Actions) на каждый PR и push в `develop`/`main`: `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo test` (matrix: `windows-latest`, `ubuntu-latest` + target `x86_64-unknown-linux-gnu`), сборка релизных артефактов на тег.
- Версионирование SemVer; changelog ведётся в `CHANGELOG.md`.
- Секреты (OAuth client id/secret, ключи подписи) — только в GitHub Secrets / локальном `.env`, никогда в репо.

## 3. Тестирование (обязательное покрытие)

Весь функционал покрывается автотестами; PR без тестов на новую логику не мёржится.

- **Юнит-тесты** (рядом с кодом): резолвер путей манифестов (Windows/Linux/Proton-маппинг), хеширование, снапшоты, merge индекса, конфликт-политики, retention бэкапов, сериализация manifest `*.ssbak`.
- **Интеграционные** (`tests/`): sync engine целиком на временных директориях (сценарии: выгрузка→загрузка на «двух устройствах», конфликт-ветвление, keep-both, откат, импорт бэкапа). Бэкенды — через trait + mock-реализацию; реальные Яндекс/Drive тесты — за feature-flag с секретами, опционально в CI.
- **LAN:** интеграционный тест двух демонов на loopback (mDNS мокается/подменяется прямым endpoint).
- **E2E smoke:** скрипт-прогон «сейв изменился → sync → второе устройство применило» на фиктивной игре.
- Минимум покрытия: core-логика (engine, манифесты, конфликты, бэкапы) — целимся в 80%+ по строкам; UI — только логика состояний, без пиксельных тестов.
- Кроссплатформенность путей: тестовая матрица кейсов Win/Linux обязана прогоняться на обеих ОС в CI.

## 4. Установка на клиенты (основа для README.md)

README.md в репо должен содержать эти разделы (наполнить по ходу M4/M5):

**Windows:**
1. Скачать `savesync-setup.exe` (подписанный) из Releases.
2. Установщик кладёт демон + приложение, регистрирует автозапуск в HKCU Run (user-context).
3. При первом старте — экран «Подключения»: облако (OAuth в браузере) и/или LAN-pairing по PIN, либо «пропустить» (локальные бэкапы).

**Steam Deck (SteamOS):**
1. Desktop Mode → установщик `.sh`/flatpak-скрипт: кладёт бинарь в `~/.local/bin`, регистрирует `systemctl --user enable --now savesync.service`.
2. (Опционально) Decky Loader: установить плагин SaveSync из магазина Decky или вручную — появится шторка в Quick Access.
3. Read-only файловая система SteamOS: установка только в home, без `sudo steamos-readonly disable`.

**Общее:** требования (Windows 10+, SteamOS 3.x), обновление (проверка Releases, in-app updater), удаление (остановить демон/сервис, удалить данные `~/.local/share/savesync` / `%APPDATA%\savesync`).

## 5. Дорожная карта

- **M1** — core MVP: скелет репо (cargo workspace: `daemon`, `core`, `app`, `decky-bridge`), парсер Steam appinfo, репо `savesync-manifests` + генератор из appinfo (импортер PCGamingWiki — отдельной задачей), сканер игр, снапшоты, локальный индекс, ручная синхронизация локально, тесты, CI.
- **M2** — облачный backend (Яндекс.Диск → затем Google Drive), ручная выгрузка/загрузка, конфликты.
- **M3** — LAN: mDNS (`mdns-sd`), pairing (PIN + SPAKE2, pinned ed25519), QUIC (`quinn`), ручной синк.
- **M4** — десктопное приложение по `design/desktop-app.html` + `design-system.md`.
- **M5** — systemd-сервис + Decky-плагин по `design/decky-panel.html`.
- **M6** — бэкапы (ручные + расписание), README-установка финализировать, полировка.
- **Итерация 2** — автотриггеры (после ресерча детекта запуска/выхода на Windows/SteamOS).

## 6. Что сделать первым шагом в новой сессии

1. Прочитать `plan.md` целиком и `research/RESEARCH.md`.
2. Инициализировать cargo workspace, подключить приватный GitHub remote, настроить ветки `main`/`develop`, CI-матьику и защиту веток.
3. Открыть `design/*.html` в браузере — UI-референс.
4. Начать M1: feature-ветка `feature/core-scanner`.
