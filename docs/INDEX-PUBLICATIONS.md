# Конкурентные публикации индекса

Старый read–merge–overwrite общего облачного `index.json` заменён журналом
неизменяемых публикаций. Это обеспечивает сохранение версий при конкурентных
записях без предположений о поддержке If-Match конкретным облачным API.

Каждая публикация содержит writer/device ID, логический clock и дельту новых версий/политик. Имя содержит BLAKE3 содержимого. Два клиента, прочитавшие одинаковую
старую историю, создают отдельные объекты; ни один не перезаписывает другой.
Чтение объединяет версии из всех объектов, проверяет checksum и отклоняет
несовпадающие записи одного immutable version ID. Ветвления остаются конфликтами.
Повтор после неизвестного результата HTTP безопасен: дополнительные одинаковые
объекты Drive не создают новых версий.

Snapshot objects также content-addressed. Индекс публикуется после архива.
Google использует плоскую область appDataFolder: гонка создания двух папок с
одинаковым именем не разделяет историю на невидимые ветки. Metadata + содержимое
передаются multipart до 5 MiB и resumable upload для больших файлов. Яндекс
использует плоские имена в настроенном root. Имена с одинаковым hash содержат
одинаковые байты. Все страницы listing читаются, включая историю свыше 1000 объектов.

Прежний `index.json` и старые snapshot folders читаются как migration source,
но новые клиенты их не перезаписывают. Google читает все совпавшие legacy roots.
**Обновите все устройства:** старый клиент не видит новый журнал. Автоматическое
удаление/компактация журнала не включено. No-op публикации подавляются; metadata
растёт с реальными изменениями, а не с каждым неизменённым sync. Hash-verified
кеш хранит immutable records в памяти и на диске: новые sync скачивают новые
records, а не весь журнал. Listing по-прежнему определяет membership и читает
все страницы. Кеш не превращает удалённый/чужой объект в доступный на канале.
История уже потерянная старым overwrite-протоколом сама не восстанавливается.

FsBackend и сервер LAN объединяют версионную историю под межпроцессным file lock,
затем пишут tmp + flush + rename. Снапшот с уже существующим ID нельзя заменить
другими байтами. Engine сохраняет оригинальный cached archive при неизменённом
контенте, вместо повторной упаковки под прежним ID.

## Локи

Для облака последний record каждого writer определяет его собственный lock state;
отсутствие своего lock — явное освобождение. Копия чужого lock из старого read
не продлевает его. Heartbeats по-прежнему имеют TTL. Эти локи — advisory guard,
а не линейризуемый распределённый mutex: одновременный захват при отсутствии
связи возможен. Разные сейвы сохраняются отдельными ветками, вместо потери версии.
Не запускайте одну игру одновременно на нескольких устройствах, если хотите
избежать ручного разрешения конфликтов.

## Проверки

Тесты запускают восемь независимых stale writers для каждого облачного mock API
и FsBackend, затем проверяют сохранение всех веток. Дополнительно проверяются
checksum, конфликт immutable IDs, lock release, duplicate legacy roots, pagination
свыше 1000 файлов и resumable upload. Обычный smoke проверяет CLI/IPC и QUIC LAN.
Живые облачные аккаунты эти mock tests не заменяют.
