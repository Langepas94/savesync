# План: SaveSync — клиент синхронизации сохранений (Windows + SteamOS)

Стек: **Rust**. Только планирование, код не пишем.

---

## 0. Общая архитектура

Один Rust-демон (core) + несколько тонких UI:

```
┌─────────────────────────────────────────────────┐
│  UI-слои                                        │
│  ├─ Десктопное приложение (Windows / SteamOS)   │
│  ├─ Decky-плагин «шторка» (тонкий клиент)       │
│  └─ (опц.) CLI                                  │
├─────────────────────────────────────────────────┤
│  savesync-daemon (Rust, единый бинарь)          │
│  ├─ Watcher (notify) — следит за папками сейвов │
│  ├─ Sync engine — версии, конфликты, дельта     │
│  ├─ Backends: YandexDisk / GoogleDrive / LAN    │
│  ├─ Discovery: mDNS + pairing                   │
│  └─ IPC: локальный gRPC/JSON-RPC сокет          │
└─────────────────────────────────────────────────┘
```

Ключевое решение: **вся логика — в демоне, UI — тонкие клиенты по IPC**. Это сразу решает проблему Decky (его плагины — Python+React, Rust там жить не может напрямую): шторка просто общается с уже запущенным Rust-демоном.

- Windows: демон как фоновый процесс / Windows Service (auto-start).
- SteamOS: systemd user unit (`savesync.service`), autostart при входе в Game Mode через Decky-инжект или desktop-файл.
- IPC: Windows — named pipe, Linux — unix socket; протокол один (JSON-RPC или tarpc).

GUI-крейт: кандидаты **egui** (нативно, лёгкий, один бинарь) или **Tauri** (если хотим переиспользовать дизайн-мокапы на HTML). Решить после дизайна.

## 1. Как игры/сейвы «находят друг друга» (идентификация)

Проблема: игра может быть установлена не из Steam (GOG, Epic, пиратка, standalone) на любой из платформ, и пути сейвов на Windows и Proton разные. Поэтому привязка к Steam appid — лишь один из сигналов, а не основа.

**Логический ключ игры — не Steam-зависимый:**
```
game_key = нормализованное имя игры (slug, например "elden-ring")
```
Одна игра = один `game_key` независимо от магазина и платформы. Оба устройства, сканируя диск, приходят к одному `game_key` независимо от того, откуда установлена игра.

**Как устройство определяет, какие игры у него есть (по приоритету):**
1. **Локальный Steam appinfo** (`appinfo.vdf` Steam-клиента): содержит UFS-конфиги Steam Cloud (корни `%WinAppData%`, `%XdgDataHome%`, Proton-маппинг, паттерны файлов) — парсим локально, без внешних зависимостей. Покрывает Steam-игры с включённым Steam Cloud.
2. **Свой репозиторий манифестов `savesync-manifests`** (см. §1.1): наша схема YAML, снапшот вендорится/обновляется из GitHub Releases. Покрывает не-Steam игры и игры без Steam Cloud.
3. **Ручное добавление**: пользователь указывает exe/папку сейвов → матчим на манифест или создаём `custom:<slug>`-запись.
4. **Подтверждение матчинга**: неуверенный матч — спрашиваем пользователя.

## 1.1. Свой пайплайн данных о путях сейвов (без сторонних зависимостей)

- **Репо `savesync-manifests`** — наш, открытый. Схема: `game_key` → пути per-ОС (Windows / native Linux / Proton `compatdata`), include/exclude, флаги «сейв в реестре Proton», «непереносим (SteamID/machine-bound)».
- **Наполнение:** (a) генерация из локального Steam appinfo — офлайн-инструмент, наш; (b) свой импортер PCGamingWiki (бесплатный MediaWiki API) — офлайн-инструмент; лицензия PCGW — CC BY-NC-SA → репо манифестов лицензируем CC BY-NC-SA с атрибуцией; (c) комьюнити-вклад: кнопка «поделиться правилом» в приложении → PR в репо (модель ProtonDB/Lutris).
- **Рантайм:** клиент тянет снапшот манифестов из GitHub Releases нашего репо (опционально) либо работает на вендоренной копии. Никаких чужих API в рантайме.

**Матчинг между устройствами:** через `game_key` в общем индексе (`index.json`). Если на Deck игра из Steam, а на ПК — из GOG, обе установки резолвятся в один `game_key` → синхронизируются. Записи `custom:*` матчатся по slug + отпечатку правил, с ручным подтверждением на втором устройстве.

## 2. Синхронизация через Яндекс.Диск / Google Drive

**Модель данных в облаке:**
```
SaveSync/
  index.json                    # реестр игр, устройств, версий (под блокировкой)
  devices/<device_id>.json      # манифест устройства
  saves/<game_key>/
    v<timestamp>_<device>_<hash>.zip   # иммутабельные снапшоты
    latest -> указатель в index.json
```
- Снапшоты иммутабельны → конфликт = две ветки версий, а не битый файл.
- Перед записью новой версии — compare-and-swap по `index.json` (etag/revision в обоих API).

## 2.1. Стратегия синхронизации (явно)

**Базовый принцип: синхронизируются снапшоты, а не «живые» папки. Один `game_key` = одна линия версий с ветвлениями.**

**Когда синхронизируем (триггеры):**

> **MVP (итерация 1): только ручной триггер.** Пользователь жмёт «Синхронизировать» — никаких таймеров, опросов облака и автоматики. Загрузка/скачивание происходят по явному действию. Это снимает вопросы polling'а, расхода трафика и гонок на старте.

> **Итерация 2 (требует ресерча, отложено):** автоматические триггеры —
> 1. Выход из игры (детект завершения процесса) → снапшот → выгрузка;
> 2. Проверка перед запуском игры;
> 3. Периодический rescan;
> 4. Распространение событий: LAN-push между демонами + etag-опрос облака.
> До ресерча механизм детекта запуска/выхода (Windows: ETW vs опрос процессов; SteamOS: события Steam через Decky) и способ оповещения между устройствами НЕ утверждены.

**Что считается «новой версией»:** снапшот с бóльшим timestamp И изменённым контент-хешем (blake3). Пустые изменения (хеш совпал) версию не создают.

**Направление:** двустороннее, per-game. «Источник правды» — вершина линии версий в индексе. Устройство, чья локальная версия отстаёт, подтягивает; чья впереди — выгружает.

**Конфликт** = обе стороны сделали снапшот от одной базы (ветвление). Политика per-game:
- «Авто: последний по времени» (по умолчанию для простых игр);
- «Спрашивать» (по умолчанию для игр с длинными кампаниями) → UI сравнения в полном приложении;
- «Keep both»: проигравшая ветка сохраняется как боковая версия, всегда можно откатить.
- Любой авто-выбор всегда обратим — проигравшая версия не удаляется.

**Локи:** пока игра запущена хотя бы на одном устройстве — её `game_key` залочен в индексе (lock с heartbeat), синхронизация этой игры на других устройствах ждёт. Это убивает целый класс конфликтов «играли одновременно». Демон на другом устройстве, видя lock, может предупредить при попытке запуска той же игры.

**Распространение событий (итерация 2, требует ресерча — НЕ входит в MVP):**
- **LAN:** после выгрузки снапшота демон пушит пирам «индекс обновлён» по открытому QUIC-соединению (или bump mDNS TXT) → задержка доли секунды, скачивание напрямую с пира.
- **Облако:** push-канала нет → дешёвый опрос: etag/HEAD-проверка `index.json` раз в 1–2 мин + внеочередные проверки по системным событиям (старт демона, выход из сна, появление сети). Худший случай — пара минут.
- **Принцип «синхронизировано заранее»:** скачивание происходит сразу по событию в фоне, а не в момент запуска игры — к запуску сейв уже локально актуален.

**Страховки на момент запуска игры (итерация 2):**
1. Детект старта процесса (Deck — события запуска/остановки от Steam через Decky; Windows — опрос процессов/ETW по известным exe из манифеста). Если обнаружена более свежая версия в окне до чтения сейва игрой — авто-подтягиваем (по политике) или уведомляем. Это race → только страховка, не основной механизм.
2. Опциональный режим «запускать через SaveSync» (per-game): клиент сначала дожидается синка, потом стартует игру. Нулевой риск устаревшего сейва.

**Защита от потери:** перед любым затиранием локальных сейвов — локальный бэкап текущего состояния (хранится N последних, настройка retention).

**Яндекс.Диск:**
- OAuth 2.0 (installed app, loopback redirect), REST API `cloud-api.yandex.net/v1/disk`.
- Альтернатива: WebDAV-эндпоинт `webdav.yandex.ru` — проще для загрузки, но хуже метаданные.
- Ревизии файлов в API нет у всех тарифов → версионирование делаем сами (иммутабельные снапшоты), облачные ревизии — только как страховка.

**Google Drive:**
- OAuth installed-app flow, Drive API v3, `appDataFolder` scope (скрытая папка приложения — не мусорит в диске пользователя) ИЛИ видимая папка — вынести в настройки.
- `files.list` с `pageToken` + Changes API для инкрементального опроса.

**Движок синхронизации (общий для обоих):**
1. **Watcher** (crate `notify`) + rescan + детект выхода процесса игры → debounce 5–15 c.
2. Хеширование (blake3) → контент не изменился — ничего не делаем.
3. Снапшот: zip/zstd → загрузка → атомарное обновление `index.json`.
4. Конфликты, локи и политики — см. §2.1.

## 2.2. Бэкапы (создание, хранение, передача)

Отдельная функция, независимая от синхронизации:

- **Ручной бэкап:** в карточке игры «Создать бэкап» → снапшот упаковывается в переносимый файл `*.savesync-backup` (zip/zstd + manifest.json: game_key, версия, устройство, дата, хеши) в выбранную папку (в т.ч. USB/внешний диск).
- **Авто-бэкапы:** по расписанию (напр. раз в день/неделю, per-game или все игры) в назначенную папку; retention — сколько копий на игру хранить, старые ротируются.
- **Импорт:** «Восстановить из файла» — читаем manifest, регистрируем как новую версию в линии игры (видна в истории, можно откатиться).
- **Передача:** файл бэкапа самодостаточен — его можно скинуть на другой ПК любым способом (флешка, мессенджер, облако вручную) и импортировать там, даже без аккаунта и pairing.
- Локальные авто-бэкапы перед затиранием (из §2.1) хранятся отдельно от пользовательских — это страховка движка, а не пользовательская функция.

## 3. Обмен по локальной сети (LAN)

**Discovery:**
- **mDNS** (crate `mdns-sd`): сервис `_savesync._tcp.local`, в TXT — device_id, имя, версия протокола, порт.
- Fallback: UDP-broadcast (если mDNS порезан роутером/AP isolation) + ручной ввод IP.

**Pairing (первое доверие):**
- На одном устройстве показывается **6-значный PIN**, на другом вводится → SPAKE2-рукопожатие с SAS-подтверждением → обмен долгоживущими pinned ed25519-ключами устройств. (QR отпадает — камер нет.)
- Дальше весь трафик шифруется (TLS с pinned-ключами или Noise protocol / QUIC из `quinn`).

**Транспорт:**
- TCP или QUIC-стримы; протокол: запрос индекса → diff версий → передача недостающих снапшотов (по сути тот же sync engine, backend=LAN).
- LAN быстрее облака → приоритетный канал (см. «Каналы независимы» ниже).

**Каналы независимы.** Облако и LAN — два самостоятельных «бэкенда» одного sync engine. Пользователь может настроить любой из них, оба или ни одного (тогда только локальные бэкапы §2.2). В UI это два независимых блока настроек, а не шаги одного визарда; pairing устройств не требует облака, облако не требует pairing. Если настроены оба — LAN приоритетнее (быстрее), облако работает как офлайн-посредник и бэкап.

**Режимы:**
- P2P-на-лету (оба устройства онлайн) — мгновенная синхронизация.
- Через облако (устройства никогда не онлайн одновременно) — офлайн-режим.
- Гибрид: индекс мержится из обоих источников.

## 4. Decky Loader и «шторка»

Факты про Decky: плагин = **React-фронтенд + Python-бэкенд**, общаются по JSON-RPC; фронт живёт в Quick Access Menu («шторка», узкая панель ~360px).

**Архитектура:**
```
Decky QAM (React UI) ⇄ Decky Python backend ⇄ savesync-daemon (Rust) по unix socket
```
- Python-бэкенд плагина — тонкий прокси к нашему демону (может и просто пробрасывать вызовы).
- Демон ставится отдельно (systemd user service), Decky-плагин — только UI. Если Decky не установлен — демон всё равно работает, управление через десктопное приложение в Desktop Mode.

**Ограничения шторки (учесть в дизайне):**
- ширина ~360px, тёмная тема Steam, навигация геймпадом;
- нельзя блокировать UI длительными операциями — только статусы и кнопки;
- минимум текста, крупные контролы;
- **конфликт-резолвер в шторке НЕ делаем** — только баннер «есть конфликт» + deeplink в полное приложение/Decky-вкладку; шторка = статус + «sync now»;
- Decky хрупок к обновлениям Steam-клиента — демон обязан жить автономно, плагин — только UI.

**Windows-аналог:** системный трей (tray-rs / tauri tray) с тем же набором быстрых действий.

## 6. Риски и упущенное (по итогам ресерча, полный отчёт — research/RESEARCH.md)

**Непереносимые сейвы (нужен свой блок/варн-лист):**
- FromSoftware (DS3, Elden Ring) шифруют сейв ключом от SteamID64; GameMaker `secure_save` привязан к машине; встречается бинарная несовместимость Win↔Linux. Открытые базы путей это НЕ покрывают — ведём свой список с пояснением пользователю (часть `savesync-manifests`).

**Надёжность детекции изменений:**
- inotify под Proton НЕ ловит mmap-записи (игры mmap'ят сейвы) → модель: watcher + debounce + периодический rescan + триггер «процесс игры умер».
- Proton-сейвы могут жить в реестре префикса (`*.reg`, HKCU) — экспорт веток, иначе перенос неполный.

**Хранилище версий:**
- Контент-адресуемое хранилище (blake3/SHA-256) + zstd: дедупликация, 10 версий 2-ГБ сейва ≈ ~2 ГБ. Облачные ревизии Яндекса (14/90 дней) ненадёжны — историю строим только у себя.

**ОС-специфика:**
- Windows: только user-context агент, НЕ SYSTEM-сервис (SYSTEM видит чужой %APPDATA%/HKCU). Код-сайнинг обязателен — неподписанные Rust-бинари ловят антивирусные false-positives.
- Windows Firewall: пользователь разрешает сеть Private, а она Public → mDNS молча мёртв. Диагностика + подсказка в UI.
- Linux keyring: дефолтный keyutils-backend не персистентен → Secret Service + fallback для Gaming Mode на Deck.
- Steam Deck: suspend во время синка — ингибиторы сна на время передачи.

**OAuth:**
- Google: `access_type=offline` + `prompt=consent`; приложение в статусе «Testing» убивает refresh-токены за 7 дней → верификация приложения или напоминание; рефреш по 401.
- Яндекс: scope `app_folder`, токен ~год, REST предпочтительнее WebDAV (у WebDAV лимит 2 ГБ на файл).

**Анти-паттерны:**
- rclone/mount как бэкенд — ловушка (только push, 20-секундное окно без локов → затирание свежего сейва). Свой REST-клиент для 1–2 провайдеров.
- Синк «живой» папки (Dropbox/Syncthing-стиль) — анти-паттерн; только снапшоты + локи.
- libp2p избыточен; QR-pairing бессмысленен (нет камер) → PIN + SPAKE2 + pinned ed25519.

**Конкуренты:** референс идей — Hoard (AGPL: смотреть идеи можно, копировать код нельзя). Рынок выигрывает не скорость копирования, а конфликт-логика (keep-both, локи, версии). Данные — только свои (§1.1).

**Прочее:** >2 устройств — топология не P2P-пара, индекс мержится многосторонне; Яндекс — регистрация app id, Google — верификация scope.

## 7. Этапы (после утверждения плана)

1. **M0** — ресерч-отчёт + дизайн-мокапы (сабагенты, идут сейчас).
2. **M1** — core MVP: манифесты, сканирование игр, снапшоты, локальный индекс, **ручная синхронизация** (кнопка), без автотриггеров и таймеров.
3. **M2** — облачный backend (один из двух, затем второй), ручная выгрузка/загрузка, конфликты.
4. **M3** — LAN: mDNS, pairing, ручной синк напрямую.
5. **M4** — десктопное приложение (Windows + Linux).
6. **M5** — systemd-сервис + Decky-плагин (шторка).
7. **M6** — бэкапы (ручные + расписание), полировка.
8. **Итерация 2** — автотриггеры: детект запуска/выхода игры, распространение событий (LAN-push, опрос облака), локи. Перед началом — ресерч доступных механизмов детекта на Windows и SteamOS.
