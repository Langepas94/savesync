# Ресерч-отчёт: подводные камни кроссплатформенной синхронизации сохранений (Windows PC ↔ Steam Deck), стек Rust

Дата: 2026-11-24. Проект: клиент синхронизации сейвов Windows ↔ SteamOS/Linux.

---

## 1. Расположение сохранений

### 1.1. Где лежат сейвы

**Windows (нативно):**
- `%APPDATA%` (`C:\Users\<user>\AppData\Roaming`)
- `%LOCALAPPDATA%`
- `AppData\LocalLow` (типично для Unity-игр, напр. Valheim: `…\LocalLow\IronGate\Valheim\worlds_local\`)
- `C:\Users\<user>\Documents` (в т.ч. локализованные варианты — «Документы», и перенаправленные через OneDrive!)
- `C:\Users\<user>\Saved Games`
- `%PUBLIC%`, `%PROGRAMDATA%`, реже `%WINDIR%`
- **Реестр**: часть игр хранит прогресс в HKCU — это не файлы, их надо экспортировать отдельно.

**Linux (нативные сборки):**
- `~/.local/share/<Game>/` (XDG_DATA_HOME)
- `~/.config/<Game>/`
- legacy: `~/.<gamename>/`

**Linux через Proton (важнейший случай для Steam Deck):**
- `~/.local/share/Steam/steamapps/compatdata/<AppID>/pfx/drive_c/users/steamuser/…` — внутри полное «виртуальное Windows-дерево»: и AppData, и Documents, и Saved Games повторяют Windows-структуру.
- Префикс содержит **свой реестр** (`*.reg`-файлы внутри префикса) — сейвы в реестре живут там и нигде больше.
- У каждой игры свой AppID в пути; для «не-Steam» игр, добавленных в Steam, AppID — генерируемый (большое число), и его надо сопоставлять по имени шортката.
- Кастомные префиксы (`STEAM_COMPAT_DATA_PATH`) ломают стандартную схему поиска — Ludusavi это пока не умеет из коробки (см. discussion #502).

**Подводные камни путей:**
- Одна игра → разные пути на двух ОС; маппинг Windows-путь ↔ Proton-путь не тривиален (слеши, `steamuser` вместо имени пользователя, разные буквы дисков).
- Симлинки: игра или обновление может молча заменить симлинк настоящей папкой.
- Общая NTFS-библиотека/партиция — плохая идея: Fast Startup оставляет NTFS «полу-гибернированной» (Linux монтирует read-only), Proton на NTFS страдает от проблем с правами и именами файлов.
- Документы на Windows часто перенаправлены в OneDrive — путь `%USERPROFILE%\Documents` может физически лежать в `OneDrive\Documents`; надо резолвить через Known Folders API (SHGetKnownFolderPath), а не конкатенировать строки.

### 1.2. База манифестов Ludusavi

- Есть, открытая, MIT: репозиторий `mtkennerly/ludusavi-manifest`. Покрывает 10 000–20 000+ игр, первичный источник данных — PCGamingWiki.
- Формат: YAML, секции `files` / `registry`, с плейсхолдерами `<root>`, `<base>`, `<home>`, `<winAppData>`, `<winLocalAppData>`, `<winLocalAppDataLow>`, `<winDocuments>`, `<winPublic>`, `<winProgramData>`, `<xdgData>`, `<xdgConfig>`, `<storeGameId>`, `<storeUserId>`, `<osUserName>`. Поддерживаются glob-паттерны и store-specific правила для `<base>` (напр. Steam: `<root>/steamapps/common/<game>`).
- **Можно и нужно переиспользовать** (MIT). Это делают и другие: Hoard, Game Backup Monitor импортируют этот же манифест. Ludusavi как crate — не библиотека («ludusavi is not a library»), поэтому манифест берём как данные и пишем свой резолвер плейсхолдеров.
- Нюансы: записи с `os: windows` могут быть единственным подтверждённым расположением файла, даже если файл есть и на других ОС; нужен лимит рекурсии для алиасов; игнорировать относительные пути (`./`, `../`).
- Дополнительно: «secondary manifest» — файл `.ludusavi.yaml` в папке установки игры; стоит поддержать.
- Свои записи: кастомные игры пользователя (custom entries) — обязательная фича, манифест не покрывает всё.

## 2. Почему Steam Cloud не решает задачу

1. **Покрытие**: Steam Cloud работает только для Steam-игр, у которых разработчик включил и правильно настроил Auto-Cloud. GOG, Epic, itch.io, эмуляторы, standalone — вне зоны.
2. **Кроссплатформенность не гарантирована**: у Auto-Cloud есть понятие «root» с ограничением по ОС. Если разработчик оставил root привязанным к Windows — сейвы между Windows и Proton не синкаются вообще (классический пример — BioShock Infinite: тихий фейл синка Windows→Linux). Часть разработчиков вообще синкает только конфиги, а не сейвы.
3. **Нет истории**: Steam хранит только «текущее» состояние. Битый сейв с одного устройства затирает хороший на всех. Отката нет.
4. **Лимиты**: per-game квота на объём и число файлов, задаётся разработчиком; большие сейвы не влезают.
5. **Конфликты при одновременной игре**: если поиграл на Deck, не дождался синка и запустил на ПК — конфликтный диалог «какую версию оставить», легко ошибиться. Steam не блокирует одновременный запуск.
6. **Не-Steam игры**: не поддерживаются совсем.
7. **Сетевые факторы**: антивирусы/файрволы режут фоновый синк; iCloud Private Relay ломал синк на macOS; синк идёт только при выходе из игры — force-quit/sleep на Deck прерывают загрузку.

### 2.1. Сейвы, которые ломаются при переносе между ОС/аккаунтами

- **Шифрование с привязкой к SteamID**: FromSoftware (Dark Souls III, Elden Ring — формат SL2) шифруют сейв ключом, производным от SteamID64. Перенос между аккаунтами/иногда устройствами требует патчера; «честное» копирование файла не работает.
- **Привязка к машине**: GameMaker `ds_map_secure_save()` привязывает сейв к конкретной машине — облачный сейв бесполезен на другом устройстве. Аналогичные механизмы есть и у других движков.
- **Endianness / бинарная несовместимость форматов**: исторически часть движков писала платформозависимый бинарный дамп. Свежий пример: dhewm3 (Doom 3 source port) — сейвы, перенесённые Linux↔Windows, загружаются «с начала уровня», а не с точки сохранения (issue #676, обе платформы на одной версии порта).
- **Нативная Linux-сборка ≠ Windows-сборка**: даже если игра есть в нативном виде на Linux, формат и расположение сейва могут отличаться. Надёжная стратегия — на Linux принудительно гонять Windows-версию через Proton (Properties → Compatibility), тогда файлы идентичны.
- **Пути внутри сейва**: некоторые игры сохраняют в сейв абсолютные пути или имя пользователя ОС (`steamuser` vs реальное имя) — перенос может «работать», но с побочками.
- **Реестр**: сейвы в HKCU на Windows живут в настоящем реестре, на Proton — в `*.reg` префикса. Кросс-перенос требует экспорта/импорта веток, а не копирования файлов.
- **Права и регистр имён**: NTFS (регистронезависимая) → ext4 (регистрозависимая): файлы `Save.dat` и `save.dat` — разные; потеря/смена прав, executable-бит; Proton может создавать имена, невалидные для NTFS.

**Вывод для продукта:** нужен per-game «блок-лист/варн-лист» непереносимых игр (манифест Ludusavi этого не покрывает — это ваша добавленная ценность) и обязательная верификация после восстановления (хэши до/после).

## 3. Облачная синхронизация из Rust

### 3.1. Yandex Disk REST API

- OAuth 2.0: регистрация приложения на oauth.yandex.ru, скоупы `cloud_api:disk.read`, `cloud_api:disk.write`, `cloud_api:disk.info`, опционально `cloud_api:disk.app_folder` (доступ только к папке приложения — рекомендуется по принципу минимальных прав; пути тогда адресуются с префиксом `app:/` вместо `disk:/`, иначе 403).
- Токен Яндекса живёт ~1 год, есть refresh token. Для desktop-приложения — flow с локальным redirect (localhost:port) или device code.
- Загрузка: двухстадийная (получить URL для upload → PUT). Большие операции (копирование/перемещение) асинхронные — отдают `202` + operation id, надо поллить статус.
- **Версионирование**: Яндекс.Диск хранит историю версий файлов — 90 дней при платном Яндекс 360, 14 дней бесплатно; версии не занимают квоту. Через веб-UI восстановление есть; через публичный REST API управление ревизиями ограничено — **не рассчитывайте на серверные ревизии как на основную историю**, делайте свои версии (имена с timestamp/хэшом).
- **WebDAV** (`webdav.yandex.com:443`) поддерживается, но: лимит файла 2 ГБ против ~50 ГБ через REST; нет корзины, публичных ссылок и async-операций. rclone и независимые клиенты выбирают REST по этой причине. WebDAV — только как fallback с app-password.
- Rate limits: официально жёсткие числа не публикуются, но при массовых операциях встречаются 429/троттлинг — нужен экспоненциальный backoff и ограничение параллелизма (аналог `--transfers=1`).

### 3.2. Google Drive API v3

- OAuth «installed app»: тип клиента Desktop, loopback redirect `http://127.0.0.1:<port>` (rclone занимает 53682 — не конфликтовать). **Обязательно** `access_type=offline` + `prompt=consent`, иначе refresh token при повторной авторизации не выдадут.
- Грабли refresh-токенов: истекают при отзыве пользователем, при 6 месяцах неиспользования, при >50 выданных токенов на аккаунт (старые отмирают), а для приложений в статусе «Testing» на OAuth consent screen — **через 7 дней**. Приложение надо переводить в Production или готовить UX повторной авторизации.
- Кэшируйте access token, рефрешьте только по 401/истечении — не на каждый запрос (rate limit на token endpoint).
- Версионирование: `keepRevisionsForever` + revisions API работает, но ревизии едят квоту, а без keepForever Google чистит старые версии (~30 дней / 100 ревизий). Своя история надёжнее.
- client_secret desktop-приложения Google формально «не секретом» не считает защищаемым, но refresh-токены пользователя — только в OS keychain (см. §6).

### 3.3. rclone как бэкенд

Так делает Ludusavi: конфиг `cloud.remote`, вызовы внешнего `rclone` (проверена совместимость с 1.62.2).

**Плюсы:** 40+ провайдеров из коробки, зрелая обработка OAuth/retry/шифрования; любой «папкообразный» таргет (mount, Syncthing-папка, G: от Google Drive for Desktop) работает без кода.

**Минусы:**
- Внешняя зависимость: на Steam Deck rclone нет из коробки; Flatpak-сандбокс прячет системный rclone (Ludusavi таскает свой в `/app/bin/rclone`).
- **Конфликтная модель — только односторонняя**: Ludusavi умеет автоматически только push; при расхождении локалки и облака — предупреждение и стоп. Кейс discussion #436: схема через rclone-mount давала ~20 секунд на бэкап одного сейва, без локов — повторный запуск игры в этом окне затирал свежий сейв. `rclone sync` однонаправленный; `bisync` существует, но требует лок-файлов и аккуратности.
- Mount-режим медленный (нет `--fast-list`), не годится для hot-path.
- Нет нативного Rust-API: вызов CLI и парсинг вывода, хрупкость к версиям.

**Рекомендация**: свой REST-клиент для 1–2 приоритетных провайдеров (Я.Диск + Drive) поверх `reqwest`, плюс опциональная интеграция с rclone для «длинного хвоста». Дельта-синхронизации у обоих провайдеров по сути нет (только целые файлы) — дедупликация и история на вашей стороне: контент-адресуемое хранилище (SHA-256), zstd. Опыт Hoard: 10 версий 2-ГБ сейва стоят ~2 ГБ, а не 20.

## 4. LAN-синхронизация

### 4.1. Discovery

- **mDNS/DNS-SD** — правильный выбор: crate `mdns-sd` (keepsimple1) — safe Rust, без привязки к async-рантайму (свой поток + flume-каналы, работает с tokio и без), Windows/macOS/Linux, IPv4+IPv6, реализует probing, conflict resolution, goodbye-пакеты. Альтернативы: `simple_mdns` (tokio-фича), свежий `hick` (Sans-I/O). По опыту интеграций Rust-mDNS находит пиры за ~100 мс против 1–3 с у Python-zeroconf.
- **UDP broadcast** — проще, но режется роутерами/VLAN/AP-isolation, плохо работает с несколькими интерфейсами; mDNS (224.0.0.251:5353) в домашних сетях надёжнее. Ограничение: корпоративные/гостевые сети блокируют multicast — нужен fallback на ручной ввод IP / last-known-peers.

### 4.2. Транспорт

- **QUIC (`quinn`)**: много стримов в одном соединении (метаданные + файлы параллельно, без head-of-line), 0-RTT для повторных подключений, TLS 1.3 встроен. Минус: UDP может быть задавлен роутером; стек тяжелее TCP.
- **TCP (tokio + rustls)**: скучно и надёжно; для типичных сейвов (мегабайты) разницы с QUIC почти нет, отладка проще.
- **libp2p**: избыточен для LAN-двух-узлов — тащит DHT, NAT-traversal и массу ненужных протоколов, раздувает бинарь и поверхность багов. Не рекомендуется.

### 4.3. Файрвол и ОС-нюансы

- NAT пробивать не нужно, но **Windows Defender Firewall** при первом bind попросит правило — и типичный фейл: пользователь разрешил только Private-профиль, а сеть помечена Public → discovery молча не работает. Программно: правило через `netsh advfirewall` (админ при установке) или INetFwPolicy2 COM API.
- На Steam Deck: SteamOS — read-only rootfs, но на userspace-порты это не влияет; user systemd-unit и порт >1024 обходятся без sudo.
- Порты 8080 и 1337 на Deck заняты Decky Loader (8080 часто и Syncthing) — не использовать.

### 4.4. Pairing и шифрование

- Камер ни у Deck, ни у ПК обычно нет → QR отпадает, реалистичен **короткий PIN/код (6–8 символов)**, вводимый/сверяемый на обоих устройствах. Внутри — PAKE (crate `spake2`) или сравнение SAS поверх TLS с self-signed сертификатами.
- После pairing — обмен долгоживущими device identity (ed25519), далее mutual TLS / QUIC с pinned-сертификатами. Авто-принятие устройств без подтверждения недопустимо (общие LAN в общежитиях и т.п.).
- Опционально: шифрование at-rest в облаке (argon2 → XChaCha20-Poly1305), чтобы провайдер не видел сейвы, — дифференциатор против Steam Cloud.

## 5. Decky Loader

### 5.1. Архитектура

- Плагин = **React/TypeScript фронтенд**, инжектируемый в Chromium-based UI Steam-клиента (Gaming Mode), + опциональный **Python-бэкенд**; общение фронт↔бэкенд — JSON-RPC-подобный механизм (`decky.callable`), двунаправленный. CORS для fetch из плагина не действует.
- Python-бэкенд может делать shell/файловые операции, значит **может запускать внешний Rust-бинарь/демон** через subprocess — каноничная схема: Python — тонкий прокси, логика в Rust.
- Кастомные (не-Python) бэкенды официально поддерживаются: исходник в `backend/src`, сборка кладёт бинарь в `backend/out`, в поставку попадает `bin/`. Бинари с нестатическими зависимостями (glibc) требуют тестирования на SteamOS **preview**-канале для публикации в сторе; сборка под `x86_64-unknown-linux-musl` снимает проблему версий glibc.
- **Хрупкость Decky**: лоадер ищет внутренние CSS-классы Valve по ключам в JS-бандлах Steam — обновления клиента периодически массово ломают плагины (пример: октябрьский билд 2026). Критичную логику нельзя привязывать к жизни Decky-панели.

### 5.2. «Шторка» (Quick Access Menu) и её ограничения

- UI плагина живёт в QAM (кнопка «…») — узкая боковая панель: нет окон, мало места, ввод текста экранной клавиатурой мучителен. Сложные сценарии (история версий, диффы, разруливание конфликтов) там неуместны. Оставить в QAM: статус синка, «sync now», индикатор конфликта; сложное — в desktop UI.
- Фронт пересоздаётся вместе с UI Steam — состояние хранить в бэкенде/демоне, не в React.
- Ревью в Decky-стор строгое: лишние директории отклоняются, тег `remote-binary` требует обоснования происхождения бинаря.

### 5.3. Рекомендуемая архитектура на Deck

**Отдельный systemd user-service (Rust-демон) + Decky-плагин как тонкий UI**:
- Демон: `~/.config/systemd/user/<app>.service`, `Restart=on-failure`, работает независимо от жизни Steam UI и обновлений Decky.
- Плагин общается с демоном через unix socket / loopback-порт с токеном.
- Прецеденты: Decky Cloud Save (rclone-обёртка, автор забросил → форки Decky Ludusavi и SDH-GameSync; последний делает pull при запуске игры и push при закрытии), Steamback (локальные снапшоты Steam Cloud игр, 10 последних). Их слабое место — отсутствие демона и конфликт-логики.

## 6. Общие риски

1. **Одновременная игра на двух устройствах** — главный источник потери данных. Нужны: lock/heartbeat-файл в облаке (TTL + owner device id), запрет pull поверх запущенной игры, конфликт-резолвер «keep both» (сохранить обе ветки, не затирать), детект запущенного процесса игры. Никогда не затирать локальный сейв без резервной копии (Hoard: «keeps a local copy of anything it replaces»).
2. **Файловые события и Proton**: inotify срабатывает для файлов, которые пишет Proton-процесс (это обычный userspace-процесс), **но** inotify не ловит записи через `mmap` (игры часто mmap'ят сейвы), не работает на сетевых ФС, очередь переполняется с потерей событий, пары IN_MOVED_FROM/IN_MOVED_TO сопоставляются негарантированно. Поэтому синк нельзя строить только на `notify`/inotify: надёжная схема — watcher как «подсказка» + debounce + периодический full-rescan по mtime/хэшам + триггер «процесс игры завершился». На Windows (ReadDirectoryChangesW через тот же crate) антивирус/индексаторы генерят шум — debounce обязателен.
3. **Права доступа**: на Deck всё в home пользователя `deck`, sudo не нужен; вторая библиотека на SD-карте — проверять опции монтирования. На Windows чужие профили и `ProgramData` требуют админа — работать только в профиле текущего пользователя. Если упакуете Linux-версию во Flatpak — сандбокс закроет доступ к `~/.local/share/Steam` (нужны filesystem permissions).
4. **Антивирусы на Windows**: неподписанный Rust-бинарь, массово пишущий файлы и ходящий в сеть, — кандидат на эвристический блок/карантин (Rust-бинари исторически ловят false-positives). Митигация: код-сайнинг (EV-сертификат для мгновенной репутации SmartScreen), репорты вендорам, подписанные reproducible релизы. Антивирус может блокировать и loopback-порты для IPC.
5. **systemd vs Windows Service**: на Linux — `systemd --user` unit без рута. На Windows полноценный Service (crate `windows-service`) требует админской установки; хуже того, сервис под SYSTEM видит **чужой** `%APPDATA%`/HKCU — сейвы пользователя он не найдёт корректно. **Вывод: user-context агент** (Task Scheduler / Run-key + single-instance mutex), не SYSTEM-сервис.
6. **Хранение токенов**: crate `keyring` — единый API поверх Windows Credential Manager (DPAPI), macOS Keychain, Linux Secret Service. Грабли: на Linux дефолтный backend (kernel keyutils) **не персистентен** — пропадает после logout/reboot, включать Secret Service; Secret Service требует D-Bus-сессию и запущенный GNOME Keyring/KDE Wallet — на Steam Deck в Gaming Mode проверить наличие, иначе fallback (шифрованный файл, ключ в keyring, либо plaintext с предупреждением). Лимиты размера секрета (~2,5 КБ у wincred) — refresh-токены влезают, большие blobs не хранить. Паттерн: в конфиге/БД — только ссылки, значения — в keyring.
7. **Автообновление**: SteamOS read-only rootfs не мешает обновлению userspace в home. Канонично: GitHub Releases + проверка версии + `self_update` на Windows; на Deck — через Decky-стор или свой updater. Не заменять бинарь работающего демона «под ним»: скачать рядом → перезапуск unit/процесса; проверка подписи/хэша перед заменой; maintenance lock на время идущего синка.
8. **Часы устройств**: конфликт-резолюция по mtime ломается при расхождении часов (Deck без сети легко имеет сбитое время). Использовать версионные векторы/lamport-clock или серверный timestamp; mtime — только как hint.
9. **Атомарность**: игры пишут сейвы неатомарно. Читать файл, который игра пишет прямо сейчас, нельзя: ждать quiet-period (нет событий N секунд), верифицировать хэш после копирования; при восстановлении — временный файл + rename.
10. **Сейвы в реестре**: на Windows — экспорт ветки (winreg crate / `reg export`), на Proton — копирование `*.reg` префикса. Кросс-перенос требует трансформации: пути внутри .reg различаются (`C:\users\<name>` vs `C:\users\steamuser`).

## 7. Конкуренты и аналоги

- **Ludusavi** (Rust, MIT) — эталон детекции: манифест от PCGamingWiki, плейсхолдеры путей, Proton-реестр, CLI+GUI, Decky-плагин. Слабости, которые вы можете закрыть: синк ручной (backup здесь → restore там), облако через rclone только push, конфликт = «предупредил и остановился», нет локов при медленном облаке (кейс #436 — затирание свежего сейва в 20-секундное окно бэкапа). Быстрый: полный скан ~10 с против ~2 мин у GameSave Manager.
- **Steam Cloud** — UX-эталон «работает само», но нет истории, нет не-Steam игр, кросс-платформа на совести разработчика, конфликтный диалог ошибкоопасен. Ваша ценность — ровно эти дыры.
- **Hoard** (AGPL) — зрелые идеи: контент-адресуемое хранилище (SHA-256, дедупликация версий), zstd, «каждая версия хранится», сервер позволяет синкать при выключенном втором устройстве, бэкап всего, что заменяешь, pull перед запуском игры. AGPL — смотреть идеи можно, копировать код нельзя. Тот же манифест Ludusavi под капотом.
- **OpenSave** (Go, MIT) — P2P-паринг, снапшоты + ветки для параллельных прохождений, конфликты по «родословной синка», а не по часам, блочные дельты. Ограничение P2P: оба устройства должны быть онлайн — подтверждение ценности облачного режима.
- **SaveSync** (платный, в Steam) — ниша «кооп-мир для друзей» через приватные Workshop-записи; Windows-only, closed source. Урок: транспорт через Steam даёт бесплатный NAT-траверсал, но привязывает к Steam.
- **GameSave Manager / GSM / SaveState / Syncthing** — Sync&Link-подход (папка сейва живёт внутри Dropbox-папки) — анти-паттерн: generic-синкер тащит полу-записанный файл на все машины. «Живую» папку сейвов нельзя синкать напрямую — только снапшоты после закрытия игры.
- **Decky-плагины** (Decky Cloud Save — заброшен; SDH-GameSync — pull на старте/push на выходе игры; Steamback — локальные снапшоты) — правильные триггеры, но нет демона и конфликт-логики.

### Ключевые уроки рынка

1. База путей — коммунальный ресурс (манифест Ludusavi / PCGamingWiki): не стройте свою, контрибьютите туда.
2. Побеждает тот, кто правильно решает конфликты и историю, а не кто быстрее копирует файлы.
3. Живую папку сейвов нельзя отдавать generic-синкеру — только снапшоты после закрытия игры.
4. Сервер/облако как посредник снимает требование «оба устройства онлайн» — главный недостаток P2P.
5. Steam Deck — first-class платформа: Game Mode UX через Decky, логика — в демоне.

## Приложение: рекомендуемый технологический радар (Rust)

| Задача | Рекомендация |
|---|---|
| Манифест путей сейвов | ludusavi-manifest (данные, MIT) + свой резолвер |
| Файловые события | `notify` (RecommendedWatcher) + debounce + периодический rescan + детект выхода процесса |
| LAN discovery | `mdns-sd` + fallback на ручной IP |
| LAN транспорт | `quinn` (QUIC) или tokio-TCP + rustls; не libp2p |
| Pairing | PIN + SPAKE2/SAS, ed25519 device keys |
| Облако | reqwest: Я.Диск REST (scope app_folder), Drive v3 (offline access); rclone — опциональный бэкенд |
| Хранение/история | CAS (SHA-256) + zstd, свои версии, не серверные ревизии |
| Токены | `keyring` (Secret Service на Linux) + задокументированный fallback |
| Шифрование | argon2 + chacha20poly1305 (at-rest) |
| Демон | systemd --user (Deck), user-agent + Task Scheduler (Windows); не SYSTEM service |
| Deck UI | Decky-плагин (React + тонкий backend) → IPC к Rust-демону по unix socket |
| Обновления | GitHub Releases + подпись + self_update, maintenance lock |
